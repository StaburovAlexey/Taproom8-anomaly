# Taproom 8 — браузерная 3D-игра с поиском аномалий

Taproom 8 — небольшая 3D-игра с элементами хоррора, в которой нужно искать изменения в баре. Комната каждый раз выглядит почти одинаково, но в новом цикле в ней может появиться аномалия: исчезнуть предмет, измениться текстура, закрыться дверь или возникнуть странный объект.

Проект сделан на TypeScript, Vue 3 и Three.js. Это не демо сцены и не технический прототип, а попытка пройти весь путь от идеи и моделирования до публикации готовой браузерной игры.

## Идея игры

Игра вдохновлена Exit 8 и серией Backrooms.

В начале игрок попадает в обычную комнату. Это нулевой цикл: в нём нет аномалий. Нужно осмотреть помещение и запомнить его состояние — мебель, предметы, картины, двери и детали окружения.

После этого начинаются новые циклы. Комната остаётся той же, но в ней появляется изменение. Игроку нужно решить, что произошло:

- аномалия есть;
- аномалии нет.

Если ответ правильный, игра переходит к следующему циклу. Если игрок ошибается, прохождение возвращается к началу.

Механика кажется простой, но она хорошо работает с небольшим количеством контента. Игрок не изучает карту и не прокачивает персонажа — он учится смотреть внимательнее.

## Откуда взялся Three.js

С Three.js я познакомился во время разработки 2D/3D-редактора. Сначала библиотека была для меня инструментом отображения объектов, камер и материалов, но постепенно стало интересно, получится ли применить эти знания для полноценной игры.

Так появился Taproom 8.

Здесь важно сделать уточнение: Three.js — это не игровой движок в привычном смысле. Это JavaScript-библиотека для работы с 3D-графикой в браузере. Она даёт сцены, камеры, геометрию, материалы, текстуры, загрузку моделей и рендеринг через WebGL.

Но в Three.js нет готового редактора уровней, физики, персонажей, сохранений, диалогов, игрового цикла и системы раундов. Поэтому поверх библиотеки пришлось самостоятельно собрать игровой слой:

- управление игроком и камерой;
- столкновения;
- двери;
- загрузку и подготовку уровня;
- систему аномалий;
- раунды и уровни сложности;
- звук;
- паузу и обработку потери фокуса;
- интерфейс;
- интеграцию с платформой.

Для frontend-разработчика это оказалось полезным упражнением: многие вещи, которые в больших игровых движках уже существуют как готовые подсистемы, здесь пришлось спроектировать и связать самостоятельно.

## Технологический стек

- Vue 3 — меню, настройки, HUD и мобильные контролы;
- TypeScript — игровая логика и контракты между системами;
- Three.js — 3D-сцена, камера, модели и взаимодействия;
- Vite — сборка;
- Pinia — состояние интерфейса;
- vue-i18n — русский и английский языки;
- Vitest — тестирование игровой логики;
- GLB и Draco — хранение и сжатие 3D-сцены.

Vue не управляет каждым объектом в 3D-сцене. Приложение разделено на два слоя.

Игровой слой отвечает за сцену, игрока, камеру, коллизии, двери, звук, раунды и жизненный цикл игры. Vue отвечает за экраны, HUD, настройки, меню и мобильное управление.

Между слоями используется типизированная шина событий. Например, UI не знает, как именно Three.js открывает дверь. Он отправляет событие выбора двери, а игровой координатор уже решает, можно ли выполнить действие и как оно повлияет на текущий раунд.

Это позволило не превращать корневой Vue-компонент в место, где одновременно живут меню, загрузка, пауза, звук и игровая логика.

Пример события можно представить так:

```ts
type GameEvents = {
  "interaction:door-selected": {
    doorId: string
  }
  "round:completed": {
    hasAnomaly: boolean
  }
  "game:pause-changed": {
    paused: boolean
  }
}
```

## Как устроен игровой цикл

Внутри игры есть несколько независимых состояний:

1. загрузка ресурсов;
2. подготовка уровня;
3. нулевой цикл без аномалий;
4. активный цикл с возможной аномалией;
5. ожидание ответа игрока;
6. переход к следующему циклу или сброс прохождения;
7. пауза и восстановление после возвращения во вкладку.

Каждый раунд должен корректно завершаться. Важно не только показать следующий уровень, но и вернуть сцену в исходное состояние. Поэтому аномалия применяется временно, а после ответа игрока обязательно сбрасывается.

Упрощённо переход выглядит так:

```ts
const anomaly = anomalyManager.activateForLevel(level)

function completeRound(answer: PlayerAnswer) {
  const isCorrect = answer === getExpectedAnswer(anomaly)

  anomalyManager.resetActive()

  if (isCorrect) {
    session.nextLevel()
  } else {
    session.restart()
  }
}
```

В реальном коде кроме этого учитываются состояние двери, звук, задержки анимаций и блокировка повторного ввода.

## Сцена из Blender

Сцену я собирал в Blender. Основная идея была в том, чтобы Blender отвечал за геометрию, расстановку объектов, UV-развёртки и запечённое освещение, а игровой код — за поведение объектов.

Production-сцена хранится в `public/assets/models/level.glb`. Внутри GLB есть группы, по которым движок понимает назначение объектов:

```text
Scene
  StaticGeometry
  Gameplay
    PlayerSpawn
    CorrectDoor
    WrongDoor
    AnomalyObjects
      FlipFlopObj
        Chair_easy
        Lamp_medium
        Bottle_hard
      FlipTextureObj
        Painting01_easy
        Portrait01_medium
        Sign01_hard
    SpriteAnomalyPoints
      Hallway01_easy
      Corner01_medium
      Doorway01_hard
    InteractiveDoors
  Colliders
  Lights
```

Имена объектов являются частью контракта между Blender и игрой. Суффикс `_easy`, `_medium` или `_hard` сообщает системе сложность аномалии.

В production-сцене GLB нет ни одного настоящего источника света. Группа `Lights` оставлена в структуре сцены как служебная, но освещение уже запечено в текстурах. Поэтому во время игры не нужно рассчитывать динамические тени и освещение от десятков объектов.

Это хорошо подходит для браузерной игры: картинка заранее подготовлена в Blender, а видеокарте остаётся в основном отрисовать геометрию и текстуры.

### Почему запекание оказалось сложнее, чем казалось

Запечь свет — это не просто нажать одну кнопку в Blender. Основные проблемы появились на стыке художественного результата и технических ограничений браузера.

Нужно было:

- подготовить отдельную UV-развёртку под lightmap;
- оставить достаточные отступы между островами UV;
- следить, чтобы свет не протекал с одной поверхности на другую;
- подобрать разрешение запекаемых текстур;
- избежать слишком заметных пятен на больших плоскостях;
- сохранить читаемый low-poly-стиль;
- получить одинаково предсказуемый результат для обычного состояния и аномальных вариантов.

Особенно неудобны были объекты, у которых во время игры меняется текстура. Если просто заменить материал, новая текстура может выглядеть так, будто она освещена иначе, чем окружающая сцена. Поэтому варианты текстур для аномалий нужно было готовить с учётом уже запечённого освещения.

В итоге сцена стала скорее набором заранее подготовленных визуальных состояний, чем универсальным 3D-уровнем с динамическим светом. Для этой игры это разумный компромисс: свет не меняется, зато атмосфера стабильна, а производительность предсказуема.

В коде остаётся процедурный уровень для технических сценариев и fallback-режима. Он может создавать источники света, но это не production-сцена из GLB.

## Как движок понимает, что объект связан с аномалией

При загрузке GLB движок сканирует специальные группы и регистрирует только объекты с корректным суффиксом сложности.

Есть несколько типов аномалий.

### Исчезновение объекта

Для объектов в группе `FlipFlopObj` сохраняется исходная видимость. При активации объект скрывается, а при сбросе возвращается в исходное состояние.

### Замена текстуры

Для объектов в группе `FlipTextureObj` используются две текстуры:

- обычная — с суффиксом `_v1`;
- аномальная — с суффиксом `_v2`.

Например:

```text
Blender object: Painting01_medium
Normal texture: textures/Painting01_v1.png
Anomaly texture: textures/Painting01_v2.png
```

При применении аномалии материал временно заменяется. После ответа игрока оригинальный материал восстанавливается, поэтому следующий раунд начинается с чистого состояния.

### Спрайтовая аномалия

В `SpriteAnomalyPoints` находятся Empty-объекты без меша. Они служат точками появления. При активации в нужной позиции создаётся спрайт с аномальным изображением.

Это позволяет добавлять визуальные изменения в сцену без моделирования отдельной полноценной геометрии.

### Дверные аномалии

Некоторые аномалии не привязаны к одному объекту. Например, дверь может открыться или закрыться в неподходящий момент. Такие сценарии реализованы как отдельные игровые аномалии.

Основной контракт выглядит так:

```ts
interface Anomaly {
  readonly id: string
  readonly difficulty: AnomalyDifficulty
  readonly targetObjectId: string
  readonly isApplied: boolean

  apply(): void
  reset(): void
}
```

У каждой аномалии есть `apply` и `reset`. Это простая, но важная граница: система раундов не должна знать, меняет ли конкретная аномалия видимость, текстуру, спрайт или состояние двери.

## Распределение сложности

На первых уровнях игроку чаще попадаются простые изменения. Затем доля средних и сложных аномалий увеличивается.

Пример весов:

| Уровень | Нет аномалии | Простая | Средняя | Сложная |
|---:|---:|---:|---:|---:|
| 0 | 100% | 0% | 0% | 0% |
| 1 | 30% | 56% | 14% | 0% |
| 2 | 30% | 49% | 17% | 4% |
| 3 | 30% | 35% | 28% | 7% |
| 4 | 30% | 21% | 35% | 14% |
| 5 | 30% | 17% | 35% | 18% |
| 6 | 30% | 14% | 35% | 21% |
| 7 | 30% | 11% | 31% | 28% |
| 8 | 30% | 7% | 28% | 35% |

После двух подряд раундов без аномалии игра принудительно выбирает сложный вариант. Иначе игрок может слишком долго получать пустые циклы и перестать внимательно смотреть на сцену.

Для выбора используется `ShuffleBag`. Он перемешивает пул аномалий и не даёт повторять один и тот же вариант, пока остальные варианты ещё не использованы.

## PS1-рендеринг

Хотелось получить не просто low-poly-сцену, а ощущение старой консольной игры. Поэтому PS1-эффект сделан не одним постфильтром.

Основные приёмы:

- рендеринг в уменьшенное разрешение;
- `NearestFilter` для текстур и итогового render target;
- отключённое сглаживание;
- отсутствие mipmap там, где они мешают стилю;
- flat shading;
- привязка экранных координат вершин к виртуальной пиксельной сетке;
- дизеринг через матрицу Bayer 4×4;
- отсутствие динамических теней в production-сцене.

Упрощённый фрагмент настройки текстуры выглядит так:

```ts
texture.flipY = false
texture.magFilter = THREE.NearestFilter
texture.minFilter = THREE.NearestFilter
texture.generateMipmaps = false
texture.anisotropy = 1
```

Камера сначала рисует сцену в `WebGLRenderTarget`, а затем этот результат растягивается на экран отдельным fullscreen-проходом. Так пиксельный стиль сохраняется на разных размерах окна.

Для привязки вершин используется отдельный vertex shader. Он округляет координаты после проекции на виртуальное разрешение, например 426×240.

## Оптимизация для слабых устройств

Браузерная игра запускается не только на игровых компьютерах. Её нужно было сделать пригодной для телефонов и устройств с ограниченным GPU.

Основные решения:

- запечённое освещение вместо динамических источников;
- отсутствие realtime-теней;
- Draco-сжатие GLB;
- кеширование моделей и текстур;
- загрузка ресурсов через единый `AssetManager`;
- `setPixelRatio(1)` вместо безусловного использования DPR устройства;
- уменьшенное внутреннее разрешение рендера;
- два профиля качества — normal и potato;
- `powerPreference: "high-performance"` для обычного режима и `"low-power"` для экономичного;
- освобождение материалов, текстур и геометрии при удалении временных объектов;
- nearest-фильтрация без лишней анизотропии;
- отсутствие постоянного обхода всей сцены для логики, которая может работать по заранее собранным спискам.

Профили рендера используют разные размеры:

| Устройство и режим | Высота рендера | Масштаб |
|---|---:|---:|
| Desktop normal | 480 | 0.6 |
| Desktop potato | 360 | 0.5 |
| Mobile normal | 540 | 0.85 |
| Mobile potato | 480 | 0.7 |

Название `potato` выбрано намеренно: это простой режим для слабых устройств, где важнее стабильная частота кадров, чем чёткость картинки.

При загрузке Draco-декодера в production оставляются только необходимые файлы. Это уменьшает размер сборки и не заставляет браузер скачивать лишние варианты декодера.

## Загрузка GLB

Модель загружается через `GLTFLoader`, а Draco-декодер подключается через `DRACOLoader`.

Загрузчик обёрнут в менеджер ресурсов, который:

- кеширует промисы загрузки;
- не загружает один и тот же файл повторно;
- удаляет запись из кеша, если загрузка завершилась ошибкой;
- централизованно загружает внешние текстуры;
- подготавливает материалы под нужный стиль рендера.

Кеширование здесь важно не только для скорости. Аномалии могут временно менять материалы и создавать спрайты, поэтому нужно понимать, какие ресурсы являются общими, а какие можно безопасно удалить.

## Управление, звук и пауза

На компьютере используется клавиатура и мышь. Для мобильных устройств есть экранные контролы.

В игре есть:

- фоновая музыка;
- звуки меню;
- шаги;
- открывание дверей;
- звуки окружения;
- пространственное позиционирование отдельных источников.

Отдельное внимание пришлось уделить жизненному циклу браузерной вкладки. Игра может быть поставлена на паузу из-за:

- скрытия вкладки;
- потери фокуса;
- перехода на другую страницу;
- рекламного экрана;
- события платформы.

Пауза хранится не одним boolean-флагом, а набором причин. Это важно, потому что игра не должна возобновиться после рекламного экрана, если вкладка всё ещё скрыта.

Упрощённо логика выглядит так:

```ts
const pauseReasons = new Set<PauseReason>()

function pause(reason: PauseReason) {
  pauseReasons.add(reason)
  gameLoop.stop()
}

function resume(reason: PauseReason) {
  pauseReasons.delete(reason)

  if (pauseReasons.size === 0) {
    gameLoop.start()
  }
}
```

Такой подход оказался надёжнее, чем попытка синхронизировать несколько независимых обработчиков через один флаг.

## Тестирование

Игровая логика вынесена так, чтобы её можно было проверять без запуска WebGL-сцены.

Тестами покрываются:

- переходы между уровнями;
- правильные и неправильные ответы;
- сброс прохождения;
- выбор сложности;
- отсутствие повторов в `ShuffleBag`;
- применение и сброс аномалий;
- поведение паузы;
- восстановление состояния объектов.

Это особенно полезно для аномалий. Визуально ошибка может выглядеть как «предмет не вернулся на место», но причина часто находится в игровой логике: не сбросился материал, повторно применился эффект или не очистился временный объект.

- оптимизация под слабые устройства;

Главный результат проекта для меня — не только сама игра. Это опыт сборки полноценного игрового цикла из отдельных систем, когда Three.js отвечает за графику, Vue — за интерфейс, а всё остальное приходится продумывать и связывать самостоятельно.

Если в баре что-то изменилось, игрок должен заметить это раньше, чем игра заметит его ошибку.
